# k6 load test, first run (TC-PERF-01), 2026-11-23

Status: **first measured run, not a pass.** The thresholds failed for reasons that come from the test setup, not from capacity (section 4). No capacity claim is made. Follows [architecture §8.4](c48-deployment-architecture.md) and plan NFR-PERF-01.

## 1. Setup

| Item | Value |
|---|---|
| Target | Production stack on one EC2 `t3.medium` (2 vCPU, 4 GB), Compose, `mem_limit` set per container |
| Script | `backend/test/k6/t18-hardening.js` via `backend/test/k6/run-t18.sh` |
| Load | 20 VUs, 2 min warm-up + 10 min measured; 4 of 5 iterations read `GET /api/v1/response/requests/mine?limit=20`, 1 of 5 creates a synthetic SOS |
| Path | k6 on the operator's laptop, through an SSM port-forward to nginx on `127.0.0.1:8080`. Every request therefore reaches nginx from one loopback IP, and Cloudflare is not in the path |
| Account | one seeded citizen account, one pre-issued access token for the whole run |
| Measurement | k6 summary (operator-supplied; the top part with checks and thresholds was **not** provided), Prometheus queries on the host, nginx container log |

## 3. Where the failures came from

1. **Expired token, about 9.2k `401`.** One access token was used for the whole run. The `401` volume at about 80 reads/s equals roughly 2 minutes, which fits a token that expired near minute 10. **Verified in code:** the identity access token lives at most 600 seconds (`auth.service.ts`, `accessExpiresIn`).
2. **Anti-spam on SOS creation, `429` from nginx zone `sos_per_ip`.** The nginx log shows about 10.8k `POST /requests` answered `429` (a lower bound: the log window did not cover the whole run). The limit is about 30 requests per minute per IP and all traffic shared one IP. This is the protection working, and only 514 synthetic SOS reached the database.
3. **About 12k `GET /requests/mine` answered `400` by nginx itself** (150-byte body; the Response API recorded no `400`). **Cause not found.** Candidates not yet checked: behaviour of the SSM port-forward under 20 concurrent connections, or a request-header limit in nginx.

The three groups add up to about the failure count only approximately, because the nginx log and Prometheus windows differ.

## 4. What this run does and does not show

- Shows: at 100 req/s of cheap reads the host stayed at 75 % CPU peak, kept at least 2 GB of memory available, touched swap lightly, and no connection pool queued. Server-side latency stayed below 300 ms p95 for requests that were served.
- Does **not** show: whether NFR-PERF-01 (read p95 ≤ 2 s, SOS p95 ≤ 3 s, failures < 1 %) is met. The failure threshold failed because of items 1 to 3 above. SOS creation capacity was not measured because the anti-spam limit rejects most writes by design.
- Not run: 50, 100 and 200 VU steps, login scenario (Argon2), coordinator queue reads, upload scenario with `sharp`, an unthrottled SOS run.
- Not checked: container restarts or OOM kills during the run; per-container peak memory against its `mem_limit`.
