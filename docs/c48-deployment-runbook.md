## 1. What runs where

| Piece | Location |
|---|---|
| Source and Compose file | `/opt/c48` (a plain `git clone`; each release checks out its commit) |
| Secrets | `/opt/c48/backend/.env` (mode 600, ignored by Git), generated by `init-env` |
| Release state | `/var/lib/c48/` (`releases/current`, `releases/previous`, `env.previous`, `pre-deploy/`) |
| Images | `ghcr.io/<owner>/<repository>/{identity-api,response-api,logistics-api,web}:<commit-sha>` (for this project `ghcr.io/sangvirgo/disaster-relief-management/...`, matching the packages already listed under the repository) |
| Evidence files | S3 buckets `c48-response-evidence-<suffix>`, `c48-logistics-evidence-<suffix>`, accessed with the EC2 instance role (no static keys) |
| Edge | `cloudflared` (systemd) to `127.0.0.1:8080` (nginx); nginx reads the real client IP from `CF-Connecting-IP` |

## 2. One-time host bootstrap

Prerequisites already done: EC2 with SSM, Docker + Compose, 2 GB swap, S3 buckets, instance role with the S3 policy.

```bash
sudo git clone https://github.com/sangvirgo/disaster-relief-management /opt/c48     # root owns the checkout (SSM runs as root)
cd /opt/c48 && sudo bash backend/scripts/deploy/init-env <domain> <suffix> ap-southeast-2
sudoedit backend/.env        # set IDENTITY_EMAIL_SMTP_USER / _PASSWORD / IDENTITY_EMAIL_FROM (Gmail app password) and optional Google/Gemini keys
```

`init-env` refuses to overwrite an existing `.env`, generates the RS256 key pair and every secret on the host, leaves AWS keys empty, and prints no secret. Never paste `.env` contents anywhere.

### Images: public or private

The repository is public and the images contain no secrets (the web bundle only holds browser keys), so the simplest choice is to make the four GHCR packages **public** (GitHub, Packages, package settings, change visibility, after the first push). The host then needs no token. For private packages create `/etc/c48/ghcr-token` (mode 600, a token with `read:packages`); `release` logs in with it. That token is the design's only long-lived secret; rotate it regularly.

### First release and demo data

```bash
sudo bash backend/scripts/deploy/release deploy <commit-sha>      # or let GitHub Actions do it
sudo bash backend/scripts/deploy/release status
# Demo seed: it refuses NODE_ENV=production, and NODE_ENV only accepts development, test or production
# (anything else, such as "demo", fails the services' configuration check). Override it for this one command only.
# Run as root (`sudo -i`); never `export NODE_ENV` in that shell, or later compose commands would recreate the
# APIs in development mode. The password is read without echo and is not stored.
cd /opt/c48 && read -rsp 'Demo password: ' p && echo && SEED_PASSWORD="$p" NODE_ENV=development bash backend/scripts/db/seed; unset p
```

The seed hashes the password into every demo account (including coordinator and operations accounts), so on a public URL choose a strong password, share it only with the people who demo, and rotate or remove the demo accounts before the defense. Do **not** use `scripts/db/reset-demo` on this host: it deletes the PostgreSQL volume and is meant for local development.

## 3. Releasing and rolling back

`release deploy <tag>` (the workflow runs it for every push to `main`):

1. checks out the commit, records the previous tag, saves `.env` as `/var/lib/c48/env.previous`;
2. pulls the four images (the previous ones stay on the host);
3. takes one verified pre-deploy dump of the three databases (only the latest is kept);
4. runs the migration jobs, starts the stack with `--wait`, and checks every API `/health/ready` plus `/health/live` through nginx;
5. on any failure restores the previous commit, `.env` and images automatically and exits non-zero (the pipeline turns red). The database is **not** restored automatically; restore `/var/lib/c48/pre-deploy` only if a migration changed data incompatibly (write migrations expand-then-contract so this is rare).

Manual commands: `release rollback` (one step back), `release status`. Only the current and previous tags are kept on disk; older local images are removed after a healthy release.

### AI models: primary, backup and monitoring

Each SOS advisory tries `GEMINI_MODEL`, then `GEMINI_BACKUP_MODEL` (Compose default `gemini-3.1-flash-lite`; set it empty in `.env` to disable), then Ollama when it is on. Nothing needs to change in `.env` for the backup model. A 429 pauses only that model for 15 minutes. Grafana, row "AI (Gemini chính, Gemini dự phòng, Ollama)": answers by source, failures and retries, paused models, p95 latency, Ollama calls, Ollama RAM and the memory of every container. Telegram alerts: `GeminiModelPaused`, `AiServedByOllama`, `AiAdvisoriesFailing`, `OllamaFallbackDown`, `OllamaMemoryHigh`, `OllamaSlow`.

### AI fallback model (Ollama, profile `ai-fallback`)

**Off by default.** A local test on 2026-11-25 measured 50-76 s per SOS and saw the 0.8B model miss life-threat cases and invent facts; turn it on only for a demo of the mechanism, and tell coordinators the labelled results need careful checking. Gemini stays the primary model. A small local model answers an SOS advisory only when Gemini fails, or when Gemini has not answered after `AI_FALLBACK_HEDGE_MS`. To turn it on, edit `/opt/c48/backend/.env` once on the host (`sudo -i`, then an editor; keep mode 600):

```bash
C48_AI_FALLBACK=on
OLLAMA_BASE_URL=http://ollama:11434
OLLAMA_MODEL=qwen3.5:0.8b-q8_0
OLLAMA_TIMEOUT_MS=90000
OLLAMA_NUM_CTX=4096
AI_FALLBACK_HEDGE_MS=3000     # 0 starts Gemini and the fallback at the same time
AI_FALLBACK_AFTER_FAILURES=1  # a queued SOS that already failed this many times goes straight to Ollama
```

The next release (any push to `main`) pulls the Ollama image (about 3.2 GB compressed) and the model, and starts the container after the stack is healthy. Response-api reads `OLLAMA_*` when it starts, so set them before that release. It skips the start, with a warning in the release log, when less than 10 GB is free on `/` (`C48_AI_FALLBACK_MIN_FREE_GB` changes that). A failed start never fails the release. To start it without a release:

```bash
cd /opt/c48 && source backend/scripts/dev/lib.sh
main_compose --profile ai-fallback up -d --wait ollama
main_compose --profile ai-fallback exec -T ollama ollama pull qwen3.5:0.8b-q8_0
main_compose up -d --no-deps --force-recreate response-api     # picks up OLLAMA_* from .env
```

Check: `docker stats --no-stream reliva-ollama` (about 1.4 GB while answering, measured locally) and the `c48_ai_fallback_attempts_total` metric. To turn it off, set `C48_AI_FALLBACK=off` and empty `OLLAMA_BASE_URL`; the next release removes the container (so `ContainerNotRunning` does not fire) and keeps the model in the `ollama-data` volume. The `ollama-data` volume keeps the model and is never removed by a reset.

### Resetting the demo data on the host

The data on this host is synthetic seed data, so it can be wiped and reloaded on purpose. Use the dedicated command, as root (`sudo -i`, because `backend/.env` is mode 600), from `/opt/c48`:

```bash
bash backend/scripts/deploy/reset-demo-data --reset
```

It asks you to type the public hostname (not just "ok") and to choose the password every demo account will share (at least 12 characters, typed hidden; or set `SEED_PASSWORD`). Then it: takes a verified dump of the current data in `/var/lib/c48/pre-reset` (latest only; a failed dump stops everything before anything is deleted), stops the stack, removes **only** the `c48_pgdata` volume, recreates the databases, migrates, seeds with a one-command `NODE_ENV=development` override (never written to `.env`), starts the stack and checks health. Existing sign-in sessions end because the database is replaced.

By default it never touches MinIO or S3, so evidence files already uploaded stay in the buckets as orphans. To empty the two evidence buckets as well, add the flag: `bash backend/scripts/deploy/reset-demo-data --reset --purge-evidence`. The purge runs only after the database has been rebuilt and seeded, deletes every object in `S3_RESPONSE_BUCKET` and `S3_LOGISTICS_BUCKET` (the buckets have no versioning, so it is permanent), and refuses to run if a bucket name equals `S3_BACKUP_BUCKET`. `restore-s3 --reset` never purges, because the restored data still points at those files. Do not use `scripts/db/reset-demo` on this host: it refuses production on purpose, and it ends by starting MinIO and building images locally. `AGENTS.md` now names this command and `restore-s3 --reset` next to the two local reset commands; they follow the same rules (explicit `--reset`, only `c48_pgdata`, MinIO preserved).

**Reset from the Grafana dashboard (added 2026-11-25).** The dashboard header link and the "Quản trị demo" panel "Đặt lại dữ liệu demo" open the GitHub Actions workflow `.github/workflows/reset-demo.yml`. Grafana itself runs nothing: the button is a link, so the reset needs a GitHub account with write access to the repository. Choose **Run workflow**, type `RESET`, keep or clear "Xóa luôn ảnh/video minh chứng trên S3", and run. The job (environment `production`, `main` only, same concurrency group as deploy) sends `echo <APP_HOSTNAME> | bash backend/scripts/deploy/reset-demo-data --reset [--purge-evidence]` through SSM, so the host still checks the hostname against `WEB_ALLOWED_ORIGINS`, keeps the safety dump and holds `release.lock`. **One-time setup:** put `SEED_PASSWORD=<at least 12 characters>` in the host's `backend/.env`; without it the job stops before anything is deleted. The script now stops the `observability` and `ai-fallback` containers with the stack and starts them again afterwards, so Grafana is unreachable for a few minutes during the reset.

### Annotated command reference

Every command below was run for real on 2026-11-23 unless a note says otherwise. `<instance-id>` is the EC2 instance; the AWS profile is `c48`, region `ap-southeast-2`. **The operator's laptop shell is fish**: run the repository scripts with `bash script`, and do not paste bash-only syntax (`${#VAR}`, `$(...)` in `export`) into fish. Never paste a password, token or `.env` content into a chat; the scripts below ask for the password at a hidden prompt.

```bash
# --- Reach the host (no inbound port is open) -------------------------------------------------------------
aws ssm start-session --profile c48 --region ap-southeast-2 --target <instance-id>   # opens a shell as ssm-user
sudo -i                                                                              # root shell; backend/.env is mode 600

# --- Open a laptop port to a service on the host (keep this terminal open) ---------------------------------
# nginx (the whole stack), used by the k6 runner:
aws ssm start-session --profile c48 --region ap-southeast-2 --target <instance-id> \
  --document-name AWS-StartPortForwardingSession --parameters '{"portNumber":["8080"],"localPortNumber":["8080"]}'
# Grafana from the laptop without the Tunnel (the Tunnel hostname stays; see "Grafana exposure" below):
#   same command with "3000" for both ports, then open http://localhost:3000 (user admin)

# --- Backup and restore (run as root on the host, from /opt/c48) -------------------------------------------
bash backend/scripts/deploy/backup-s3                      # on demand; the timer runs it at 19:00 UTC (02:00 Vietnam); keeps the newest 2
bash backend/scripts/deploy/restore-s3 --list              # lists complete backups in S3
bash backend/scripts/deploy/restore-s3 --verify [STAMP]    # downloads and checks SHA-256 and pg_restore --list; changes nothing
bash backend/scripts/deploy/restore-s3 --reset [STAMP]     # DESTRUCTIVE: replaces the data with that backup (asks for the hostname first)
#   Offsite copy by hand: S3 console, bucket c48-backup-*, backups/<newest>/, download the 5 files, then on the laptop:
#   cd <folder> && sha256sum -c manifest.sha256

# --- Reset demo data (DESTRUCTIVE; asks for the public hostname and a seed password) -------------------------
bash backend/scripts/deploy/reset-demo-data --reset                      # database only; S3 photos stay as orphans
bash backend/scripts/deploy/reset-demo-data --reset --purge-evidence     # also empties the two evidence buckets (permanent: no versioning)
#   Why not DELETE FROM ...: request_event is append-only (trigger). Do not bypass it; reset instead.

# --- Monitoring (profile observability; started by `release` when C48_OBSERVABILITY=on) --------------------
docker ps --format '{{.Names}} {{.Status}}'                              # containers
docker stats --no-stream --format '{{.Name}} {{.MemUsage}}'              # memory per container (limits are in compose.yaml)
free -m                                                                  # host memory; keep about 800 MB available
# After editing a rules or dashboard file by hand, recreate the containers that mount single files:
source backend/scripts/dev/lib.sh && main_compose --profile observability up --no-build -d --force-recreate --no-deps prometheus alertmanager grafana
# `release` now does this on every deploy (a plain `up -d` keeps the old inode of a replaced file).

# --- Load test (laptop; Terminal A holds the 8080 port-forward above) ---------------------------------------
bash backend/test/k6/run-t18.sh        # asks for username and password; 2 segments of 5 min (token lives 10 min); writes synthetic SOS
#   Anti-spam (about 30 SOS/min per IP) rejects most writes through the port-forward; that is expected. See docs/c48-k6-report-2026-11-23.md.
#   Clean the synthetic SOS with reset-demo-data above, not with SQL.
```

#### Grafana exposure (decision 2026-11-23, operator)

The hostname `grafana.<domain>` stays in the Cloudflare Tunnel and Grafana is reached directly over HTTPS. **Cloudflare Access was not set up**: Zero Trust asked for a payment method, which the operator declined. Protection is therefore Grafana's own login only (user `admin`, a strong password in `backend/.env`, sign-up and anonymous access disabled, cookies `Secure`). Keep that password long and unique, rotate it if it leaks (Grafana applies `GRAFANA_ADMIN_PASSWORD` only when its database is first created; change it later with `docker exec -it reliva-grafana grafana cli admin reset-admin-password <new>`, typed by the operator), and consider removing the Tunnel hostname if the dashboard is no longer needed publicly. The Tunnel health notification and the external uptime check were dropped because the operator no longer wants email alerts; Telegram alerts from Alertmanager remain.

## 4. GitHub and AWS wiring

**Decision (2026-11-22, user):** the pipeline logs in to AWS with an **IAM access key stored as a GitHub secret**, because the account's IAM "Identity providers" page is locked behind *Activate advanced features*, which the account owner has not enabled (effects on billing not verified). The design's preferred OIDC option stays the upgrade path.

Trade-off, stated plainly: the key is a long-lived credential. Anyone who can run a workflow on `main` (or who steals the key) can run a shell command as root on the host through SSM. Mitigations used here: a dedicated IAM user that can do nothing else, secrets scoped to the `production` environment (restricted to the `main` branch, invisible to pull requests and forks), no key in the repository, logs or chat, and regular rotation.

1. **IAM user** `c48-github-deploy` (no console access) with this inline policy `c48-deploy-ssm`; it can only send a shell command to this one instance and read the result:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "ssm:SendCommand",
      "Resource": [
        "arn:aws:ec2:ap-southeast-2:<account-id>:instance/<instance-id>",
        "arn:aws:ssm:ap-southeast-2::document/AWS-RunShellScript"
      ] },
    { "Effect": "Allow", "Action": ["ssm:GetCommandInvocation", "ssm:ListCommandInvocations"], "Resource": "*" }
  ]
}
```

2. **Access key** for that user (use case: command line interface). Put it into GitHub from your own terminal so it never appears in a chat or screenshot; `gh` prompts for the value without echoing it:

```bash
gh secret set AWS_ACCESS_KEY_ID     --env production --repo sangvirgo/disaster-relief-management
gh secret set AWS_SECRET_ACCESS_KEY --env production --repo sangvirgo/disaster-relief-management
```

3. **GitHub environment** `production`: restricted to the `main` branch, no manual approval (every merge deploys). **Repository variables:** `AWS_REGION` (`ap-southeast-2`), `EC2_INSTANCE_ID`, `APP_HOSTNAME` (`<domain>`, enables the external check), `VITE_GOOGLE_CLIENT_ID`, optional `VITE_GOOGLE_MAPS_API_KEY`, and finally `DEPLOY_ENABLED=true` (the `deploy` job stays skipped until it exists, so CI and image publishing work first).
4. **Rotation:** create a second key, update the two secrets, delete the old key; do this at least every 90 days and immediately if a key may have leaked.
5. Workflow summary: pull request: test and build only. Push to `main`: test, build and push images tagged with the commit SHA, deploy through SSM, wait for the result, check `https://<domain>/health/live`.
6. **Old image versions are not deleted automatically.** An automatic cleanup was tried and removed: the action looked up `identity-api` while GHCR names these packages `<repository>/<image>` (so it failed with "Package not found"), and deleting "all but the newest N" versions is unsafe because each build also creates untagged child manifests; cutting in the middle of a build could orphan a tag that is still deployed or is the rollback target. The host keeps only the current and previous images itself. Public packages have no storage charge as far as known (not verified); if cleanup is wanted later, delete whole builds older than the previous release, never by raw version count.

**Upgrade path (no stored key):** after *Activate advanced features*, create the IAM OIDC provider (`https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`) and a role trusted for `repo:sangvirgo/disaster-relief-management:environment:production`, give it the same inline policy, then switch the workflow back to `role-to-assume` with `permissions: id-token: write` and delete the two secrets and the IAM user.

## 5. Cloudflare Tunnel

1. Zero Trust, Networks, Tunnels, create a tunnel, install `cloudflared` as a systemd service on the host (the dashboard prints the command; it contains a token, so run it yourself and do not paste it into chats).
2. Public hostname `<domain>`, service `http://127.0.0.1:8080`. Cloudflare replaces the old DNS record with a proxied CNAME.
3. Verify `https://<domain>/health/live` and an SOS from a phone (GPS needs HTTPS). Check that two different phones are not throttled as one client: nginx now keys its zones on `CF-Connecting-IP` (trusted only from the Docker bridge or loopback).

## 6. Known limits and open items

- **Not yet run end to end.** The release script is covered by tests with fake `docker`/`git`/`curl`; the Docker image builds (including `sharp` on Debian slim), S3 access with the instance role, and the SSM deploy have not been exercised on a real host.
- **Test gate exclusions.** CI skips two jest suites and one node test that already fail on a clean `main` (see the comments in `deploy.yml`); remove the exclusions when they are fixed.
- **IAM role instead of per-service S3 keys.** Response and Logistics share the instance role, so the per-service bucket isolation of the MinIO setup is enforced only in application configuration, not by AWS.
- **Presigned downloads.** Signed links point at `https://s3.<region>.amazonaws.com/<bucket>/<key>` (path style). The web opens them as a link, so the page CSP is unchanged; embedding them in `<img>` or `<video>` would need the host added to `img-src` or `media-src`.
- **Real client IP trust range.** `nginx.conf` trusts `172.16.0.0/12` and loopback. If Docker allocates the Compose network outside that range, adjust `set_real_ip_from`.
- Daily backup timer, S3-aware `backup`/`object-inventory`, CloudWatch log shipping, `/metrics` and the `observability` profile are **not implemented yet** (design sections 7 and 8).
- Action versions in the workflow (`checkout@v4`, `setup-node@v4`, `docker/*`, `aws-actions/configure-aws-credentials@v4`, `delete-package-versions@v5`) were written from memory; confirm they are current before relying on them.
