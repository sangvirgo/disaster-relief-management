| Attribute | Value |
|---|---|

Placeholders: `<domain>` is the public hostname (for example `reliva.tansang.dpdns.org`), `<suffix>` the S3 bucket suffix, `<account-id>` the AWS account, `<instance-id>` the EC2 instance.

## 1. What runs where

| Piece | Location |
|---|---|
| Source and Compose file | `/opt/c48` (a plain `git clone`; each release checks out its commit) |
| Secrets | `/opt/c48/backend/.env` (mode 600, ignored by Git), generated by `init-env` |
| Release state | `/var/lib/c48/` (`releases/current`, `releases/previous`, `env.previous`, `pre-deploy/`) |
| Images | `ghcr.io/<owner>/<repository>/{identity-api,response-api,logistics-api,web}:<commit-sha>` (for this project `ghcr.io/sangvirgo/disaster-relief-management/...`, matching the packages already listed under the repository) |
| Evidence files | S3 buckets `c48-response-evidence-<suffix>`, `c48-logistics-evidence-<suffix>`, accessed with the EC2 instance role (no static keys) |
| Edge | `cloudflared` (systemd) to `127.0.0.1:8080` (nginx); nginx reads the real client IP from `CF-Connecting-IP` |

## 2. One-time host bootstrap

Prerequisites already done: EC2 with SSM, Docker + Compose, 2 GB swap, S3 buckets, instance role with the S3 policy.

```bash
sudo git clone https://github.com/sangvirgo/disaster-relief-management /opt/c48     # root owns the checkout (SSM runs as root)
cd /opt/c48 && sudo bash backend/scripts/deploy/init-env <domain> <suffix> ap-southeast-2
sudoedit backend/.env        # set IDENTITY_EMAIL_SMTP_USER / _PASSWORD / IDENTITY_EMAIL_FROM (Gmail app password) and optional Google/Gemini keys
```

`init-env` refuses to overwrite an existing `.env`, generates the RS256 key pair and every secret on the host, leaves AWS keys empty, and prints no secret. Never paste `.env` contents anywhere.

### Images: public or private

The repository is public and the images contain no secrets (the web bundle only holds browser keys), so the simplest choice is to make the four GHCR packages **public** (GitHub, Packages, package settings, change visibility, after the first push). The host then needs no token. For private packages create `/etc/c48/ghcr-token` (mode 600, a token with `read:packages`); `release` logs in with it. That token is the design's only long-lived secret; rotate it regularly.

### First release and demo data

```bash
sudo bash backend/scripts/deploy/release deploy <commit-sha>      # or let GitHub Actions do it
sudo bash backend/scripts/deploy/release status
# Demo seed: refuses NODE_ENV=production, so override it for this one command only (the stack keeps running as production).
sudo SEED_PASSWORD='<demo password>' NODE_ENV=demo bash backend/scripts/db/seed
```

The seed hashes `SEED_PASSWORD` into demo accounts. Use it only for the demo, then rotate the demo credentials before the defense.

## 3. Releasing and rolling back

`release deploy <tag>` (the workflow runs it for every push to `main`):

1. checks out the commit, records the previous tag, saves `.env` as `/var/lib/c48/env.previous`;
2. pulls the four images (the previous ones stay on the host);
3. takes one verified pre-deploy dump of the three databases (only the latest is kept);
4. runs the migration jobs, starts the stack with `--wait`, and checks every API `/health/ready` plus `/health/live` through nginx;
5. on any failure restores the previous commit, `.env` and images automatically and exits non-zero (the pipeline turns red). The database is **not** restored automatically; restore `/var/lib/c48/pre-deploy` only if a migration changed data incompatibly (write migrations expand-then-contract so this is rare).

Manual commands: `release rollback` (one step back), `release status`. Only the current and previous tags are kept on disk; older local images are removed after a healthy release.

## 4. GitHub and AWS wiring

**Decision (2026-11-22, user):** the pipeline logs in to AWS with an **IAM access key stored as a GitHub secret**, because the account's IAM "Identity providers" page is locked behind *Activate advanced features*, which the account owner has not enabled (effects on billing not verified). The design's preferred OIDC option stays the upgrade path.

Trade-off, stated plainly: the key is a long-lived credential. Anyone who can run a workflow on `main` (or who steals the key) can run a shell command as root on the host through SSM. Mitigations used here: a dedicated IAM user that can do nothing else, secrets scoped to the `production` environment (restricted to the `main` branch, invisible to pull requests and forks), no key in the repository, logs or chat, and regular rotation.

1. **IAM user** `c48-github-deploy` (no console access) with this inline policy `c48-deploy-ssm`; it can only send a shell command to this one instance and read the result:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "ssm:SendCommand",
      "Resource": [
        "arn:aws:ec2:ap-southeast-2:<account-id>:instance/<instance-id>",
        "arn:aws:ssm:ap-southeast-2::document/AWS-RunShellScript"
      ] },
    { "Effect": "Allow", "Action": ["ssm:GetCommandInvocation", "ssm:ListCommandInvocations"], "Resource": "*" }
  ]
}
```

2. **Access key** for that user (use case: command line interface). Put it into GitHub from your own terminal so it never appears in a chat or screenshot; `gh` prompts for the value without echoing it:

```bash
gh secret set AWS_ACCESS_KEY_ID     --env production --repo sangvirgo/disaster-relief-management
gh secret set AWS_SECRET_ACCESS_KEY --env production --repo sangvirgo/disaster-relief-management
```

3. **GitHub environment** `production`: restricted to the `main` branch, no manual approval (every merge deploys). **Repository variables:** `AWS_REGION` (`ap-southeast-2`), `EC2_INSTANCE_ID`, `APP_HOSTNAME` (`<domain>`, enables the external check), `VITE_GOOGLE_CLIENT_ID`, optional `VITE_GOOGLE_MAPS_API_KEY`, and finally `DEPLOY_ENABLED=true` (the `deploy` job stays skipped until it exists, so CI and image publishing work first).
4. **Rotation:** create a second key, update the two secrets, delete the old key; do this at least every 90 days and immediately if a key may have leaked.
5. Workflow summary: pull request: test and build only. Push to `main`: test, build and push images tagged with the commit SHA, deploy through SSM, wait for the result, check `https://<domain>/health/live`.
6. **Old image versions are not deleted automatically.** An automatic cleanup was tried and removed: the action looked up `identity-api` while GHCR names these packages `<repository>/<image>` (so it failed with "Package not found"), and deleting "all but the newest N" versions is unsafe because each build also creates untagged child manifests; cutting in the middle of a build could orphan a tag that is still deployed or is the rollback target. The host keeps only the current and previous images itself. Public packages have no storage charge as far as known (not verified); if cleanup is wanted later, delete whole builds older than the previous release, never by raw version count.

**Upgrade path (no stored key):** after *Activate advanced features*, create the IAM OIDC provider (`https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`) and a role trusted for `repo:sangvirgo/disaster-relief-management:environment:production`, give it the same inline policy, then switch the workflow back to `role-to-assume` with `permissions: id-token: write` and delete the two secrets and the IAM user.

## 5. Cloudflare Tunnel

1. Zero Trust, Networks, Tunnels, create a tunnel, install `cloudflared` as a systemd service on the host (the dashboard prints the command; it contains a token, so run it yourself and do not paste it into chats).
2. Public hostname `<domain>`, service `http://127.0.0.1:8080`. Cloudflare replaces the old DNS record with a proxied CNAME.
3. Verify `https://<domain>/health/live` and an SOS from a phone (GPS needs HTTPS). Check that two different phones are not throttled as one client: nginx now keys its zones on `CF-Connecting-IP` (trusted only from the Docker bridge or loopback).

## 6. Known limits and open items

- **Not yet run end to end.** The release script is covered by tests with fake `docker`/`git`/`curl`; the Docker image builds (including `sharp` on Debian slim), S3 access with the instance role, and the SSM deploy have not been exercised on a real host.
- **Test gate exclusions.** CI skips two jest suites and one node test that already fail on a clean `main` (see the comments in `deploy.yml`); remove the exclusions when they are fixed.
- **IAM role instead of per-service S3 keys.** Response and Logistics share the instance role, so the per-service bucket isolation of the MinIO setup is enforced only in application configuration, not by AWS.
- **Presigned downloads.** Signed links point at `https://s3.<region>.amazonaws.com/<bucket>/<key>` (path style). The web opens them as a link, so the page CSP is unchanged; embedding them in `<img>` or `<video>` would need the host added to `img-src` or `media-src`.
- **Real client IP trust range.** `nginx.conf` trusts `172.16.0.0/12` and loopback. If Docker allocates the Compose network outside that range, adjust `set_real_ip_from`.
- Daily backup timer, S3-aware `backup`/`object-inventory`, CloudWatch log shipping, `/metrics` and the `observability` profile are **not implemented yet** (design sections 7 and 8).
- Action versions in the workflow (`checkout@v4`, `setup-node@v4`, `docker/*`, `aws-actions/configure-aws-credentials@v4`, `delete-package-versions@v5`) were written from memory; confirm they are current before relying on them.
