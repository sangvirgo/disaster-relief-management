# 04 — Logistics service: API contract

Schema: [schema/logistics.sql](schema/logistics.sql). Conventions: [00](00-setup.md). Permissions: [05](05-permissions.md). Business rules: plan §6.4, §8.3, §22.3, §23.2/23.4, §25. Quantities are **decimal strings** validated against `unit.scale`; reject nonpositive command quantities, nonfinite/exponent/overflow and excess lexical scale before numeric(18,3) casting; count split fields may be zero; wrong scale (`QUANTITY_SCALE_INVALID`). Public routes live under `/public/…` so Nginx can rate-limit them separately; this refines the sketches in plan §25.9 (non-final). No cart, checkout, payment or money fields exist anywhere.

**Stock rule (implement as one function; details in 00 §3.1):** stock changes **only by inserting a `stock_movement`** — a database trigger applies its deltas to `stock_balance` and the balance CHECKs (`on_hand ≥ 0`, `reserved ≥ 0`, `reserved ≤ on_hand`) fire in the same statement; the application role has SELECT but no UPDATE on `stock_balance`. Per command: pre-read ids, then lock in this order — `distribution` → `fulfillment_cycle` (request-linked only) → `relief_need` → `commitment`; pre-insert missing balances in sorted `(warehouse_id, item_id)` order with `ON CONFLICT DO NOTHING`, then insert movements (unique `operation_ref`). The movement trigger performs the balance row update and serializes competing stock changes; application queries do not use `SELECT … FOR UPDATE` on `stock_balance` because PostgreSQL requires UPDATE privilege for row-locking SELECTs. Update counters, audit, and notice in the same short transaction, with no outbound call and ≤ 50 lines (`TOO_MANY_LINES`). A `stock_balance_check` violation maps to `INSUFFICIENT_STOCK`. `operation_ref` is derived from a business key (`RCPT:{receipt}:{item}`, `ADJ:{adjustment}`, `{command}:{key}:{line}`), so a replay inserts nothing. Counters on `commitment` and `distribution_line` are written only by the accounting command and reconciled against ledger/settlement sums in tests.

**Contract rules for every endpoint below:** each non-GET carries `Idempotency-Key` (00 §3) and each PATCH/deactivate/approve/review-style command on a versioned row carries `expected_version`; every list is keyset-paginated; list rows mask donor phones (`09******45`), the full number appears only in detail views for staff with the right scope.

## 5. Needs, commitments and fulfillment (request-linked aid)

Response is authoritative for the request; Logistics admits attribution through POST /internal/requests/{id}/cycles/{work_cycle}/admit on Response (service token plus signed live actor context, 2s, before opening a transaction): status ∈ {VERIFIED, TRIAGED, DISPATCHED, IN_PROGRESS}, `work_cycle`, campaign attribution, and caller's scope. Admission sets Response attribution_locked_at under the request lock before local creation; failed Logistics creation leaves conservative stamp; retry same cycle is safe.

| Method & path | Perm | Behaviour |
|---|---|---|
| `POST /needs` (Idem) | `NEED_MANAGE` | `{ request_id, work_cycle, item_id, quantity, reason? }`. Creates the `fulfillment_cycle` on first use (unique constraint, then lock the winner) and copies campaign attribution onto the **cycle** (one per request, not per need). Cycle must be OPEN (`CYCLE_FROZEN`/`CYCLE_SEALED` 409). Every need is delivered to the final recipient (relief points were removed). One live need per item per cycle (`NEED_EXISTS`). |

| `GET /requests/{request_id}/fulfillment?work_cycle=` | `NEED_MANAGE`/`REPORT_READ` in scope | `{ needs:[{ id, item, unit, original, requested, committed_reserved, issued_unsettled, delivered, outstanding, cancelled_remaining, status, contributions:{ items:[…], more } }], cycle_state, generated_at }`; `work_cycle` omitted selects the latest cycle. `outstanding = requested − delivered` for non-cancelled needs, else `0`. | `POST /internal/requests/{request_id}/cycles/{cycle}/freeze` · `/seal` · `/unseal` | Response service token (`aud=logistics`) | `freeze`/`unseal` body `{ intent_id }`; `seal` body `{ intent_id, outcome_basis: RESCUE_COMPLETED\|SUPPLY_ONLY\|NO_ACTION_REQUIRED }`. Idempotent on exact intent and body. **seal / freeze** first confirm with Response (`GET /internal/operations/{intent_id}`) that the exact request/cycle/kind intent is still `PENDING`, then lock cycle and check the durable `cycle_intent` fence; ABORTED rejects even a duplicate that previously passed remote PENDING precheck. **seal**: all bases require no OPEN/PARTIALLY_FULFILLED need, `reserved_remaining=0`, and `unsettled_issued=0` (`409 CYCLE_NOT_SETTLED` with reason codes). `SUPPLY_ONLY` also requires at least one delivered unit; `NO_ACTION_REQUIRED` requires zero delivered units. `RESCUE_COMPLETED` uses the shared settlement checks. Exact outcome basis is bound to the intent and must match on retries. A missing cycle is created and sealed for an empty cycle; the resulting `intent_id` is the seal identifier Response stores as `resolution_seal_id`. **freeze** upserts a missing cycle so delayed `POST /needs` finds it FROZEN; it blocks new needs/increases/commitments/issues while allowing release, cancel, and physical settlement. **unseal** requires Response to confirm the exact intent is `ABORTING` and the request is not RESOLVED/CLOSED. A live cycle intent must bind that exact id; a missing/unbound cycle may receive an abort fence. Unseal/unfreeze writes ABORTED under the cycle lock, even when no prior cycle/seal exists after confirmed ABORTING. No stale intent can undo a newer seal. No TTL or auto-unseal. |

Since 2026-11-26 commitments (reservations) are created only by supply requests (section 6); the manual `POST /needs/{id}/commitments` and `POST /commitments/{id}/release` routes were removed with `COMMITMENT_MANAGE`.

Every command above that is request-linked first locks `fulfillment_cycle` (SEALED ⇒ `CYCLE_SEALED`, FROZEN ⇒ only release/cancel/settlement allowed), including previously validated delayed calls. SEALED explicitly allows after-target physical custody only (below).

## 6. Supply requests (replaces distributions, handoffs and pickup tickets; user decision 2026-11-26)

A rescue team asks for goods for its own mission; the system reserves them at one warehouse and gives the team a six-digit pickup code; warehouse staff hand the goods over against that code. There is no slip, approval, dispatch, handoff, loss review, close-out or reconciliation step. Tables: `supply_request`, `supply_request_line` (migration `ReplaceDistributionWithSupplyRequests1796515200000`, which also drops `distribution`, `distribution_line`, `handoff_*`, `issued_line_settlement`, `pickup_ticket*`, `pickup_closeout_line`, `team_custody`, `commitment.returned_quantity/lost_quantity`, `stock_movement.distribution_line_id/handoff_line_id`, the `RETURN` movement type and `logistics_attachment.handoff_id`; it refuses to run while distribution or pickup data exists, so reset the demo database first).

| Method & path | Perm | Behaviour |
|---|---|---|
| `GET /supply-requests?mission_id=` | team member, team leader, or coordinator of the campaign | `{ items:[team view], can_request }`, newest first (20). The team view includes `pickup_code` while READY, the warehouse (`name`, `address_note`, `location`), lines with `requested_quantity`, `reserved_quantity`, `shortfall_quantity`, `has_shortfall` and `expires_at`. |
| `GET /supply-requests/suggestion?mission_id=` | same | Suggested lines: every OPEN/PARTIALLY_FULFILLED need of the mission's SOS cycle minus delivered and still reserved. `basis` is `AI_TEXT` (ESTIMATED by the need-extraction sweep from the SOS text), `NORM` (ESTIMATED by the norm table) or `CONFIRMED`. A proposal only; nothing is written. |
| `POST /supply-requests` (Idem) | `SUPPLY_REQUEST_CREATE`: a **leader** of the mission team (VOLUNTEER grant) or a COORDINATOR whose grant covers the campaign (`on_behalf=true`) | `{ mission_id, lines:[{ item_id, quantity }] }` (1–30 distinct items). In one transaction: lock the cycle (OPEN only); each line confirms the SOS need (ESTIMATED → CONFIRMED, requested raised to `delivered + reserved + this request` when lower; a missing need is created as CONFIRMED; audit `NEED_REQUESTED_BY_TEAM`); pick **one** warehouse (campaign PRIMARY/BACKUP first by coverage, PRIMARY wins a tie; any other ACTIVE warehouse only when no campaign warehouse holds any requested goods; none ⇒ `SUPPLY_NO_STOCK`); reserve `min(requested, free)` per line as commitment + `RESERVE` movement; lines it cannot cover keep `reserved_quantity < requested_quantity` (shortfall, still counted as open need for supply gaps). | `POST /supply-requests/{id}/hand-over` (Idem · Ver) | `SUPPLY_REQUEST_HANDOVER` | `{ expected_version, pickup_code }`. READY and not expired (`SUPPLY_REQUEST_EXPIRED`); the code must match (`SUPPLY_CODE_MISMATCH`); cycle must be OPEN. For each reserved line: `ISSUE` movement on the commitment, `issued_quantity` and `delivered_quantity` += remaining reservation, need status recomputed (FULFILLED when delivered = requested). **Expiry.** `SupplyRequestScheduler` (job `logistics.supply-request-expiry`, every 5 minutes, `C48_SUPPLY_REQUEST_JOB_ENABLED`) releases READY requests past `expires_at` and marks them EXPIRED; the movements are attributed to the requester and the audit row has a null actor.

**Locks.** Hand-over, cancel and expiry lock the request, then cycle → need → commitment (the need-command order). Create locks the cycle and does not lock an existing request row; the partial unique indexes `supply_request_live_mission_uq` and `supply_request_live_code_uq` guard concurrent creates.

**Resolution.** Sealing a cycle still requires no reserved quantity (`RESERVED_QUANTITY`), so a READY request must be handed over, cancelled or expire before the SOS is resolved. `UNSETTLED_ISSUE` no longer occurs because issue and delivery happen together.

Errors (messages in [07-error-catalog.md](07-error-catalog.md)): `SUPPLY_MISSION_NOT_FOUND`, `SUPPLY_MISSION_NOT_ACTIVE`, `SUPPLY_DUPLICATE_ITEM`, `SUPPLY_REQUEST_EXISTS`, `SUPPLY_NO_STOCK`, `SUPPLY_CODE_BUSY`, `SUPPLY_CODE_MISMATCH`, `SUPPLY_REQUEST_EXPIRED`, `SUPPLY_NOTHING_TO_HAND_OVER`, `ITEM_NOT_ACTIVE`.

## 7. Attachments

Donation/dispute uploads use `POST /public/donations/{id}/evidence?dispute_id={id}` with exactly one multipart file named `file`; the optional dispute must belong to that delivery. The service follows the Response evidence procedure (plan §23.5): reserve quota under the delivery row lock, stream outside any transaction, detect content type from file bytes, then mark READY. Limits are at most 5 attachments and 100 MiB per delivery (including its disputes), JPEG/PNG up to 10 MiB and MP4 up to 50 MiB; only the private Logistics bucket and Logistics credentials are used. ## 12. Campaign warehouse assignment (`CAMPAIGN_WAREHOUSE_VIEW` / `CAMPAIGN_WAREHOUSE_MANAGE`)

Campaign geometry (`center`, `radius_m`) is owned by Response and is read through its internal projection. Logistics keeps a local cache in `campaign_area_snapshot` and never joins across databases. A warehouse is eligible when it is `ACTIVE`, has a `location` and a `service_radius_m`, and `ST_DWithin(warehouse.location, campaign.center, warehouse.service_radius_m + campaign.radius_m)` holds in geography metres. Overlap is allowed. Each campaign has at most one `PRIMARY` (partial unique index); other eligible warehouses are `BACKUP` and informational only. The rules follow [the supply-gap proposal §3.2](../c48-supply-gap-and-goods-flow-proposal.md).

| Method & path | Auth | Behaviour |
|---|---|---|
| `GET /campaigns/{id}/warehouses` | `CAMPAIGN_WAREHOUSE_VIEW` (COORDINATOR and OPERATIONS_MANAGER; a campaign grant covers only its campaign) | Returns `{ campaign_id, campaign_status, assignment_version, area, primary, warehouses[], flags[], generated_at }`, plus `proposed_primary_warehouse_id` only when no `PRIMARY` is stored. Each eligible warehouse carries `role`, `source`, `distance_m`, `stock` (`open_needed_items`, `needed_items_in_stock`: counts of distinct items, never summed across units) and `open_supply_requests` (load: READY supply requests waiting at the warehouse). The read is strictly read-only: it fetches the latest Response area for eligibility, runs only SELECTs (no transaction, advisory lock, snapshot write, assignment change or audit row) and returns the stored `assignment_version` unchanged. `proposed_primary_warehouse_id` is the warehouse the next sync would assign (null when nothing is eligible); it is never persisted. | `PUT /campaigns/{id}/primary-warehouse` (Idem) | `CAMPAIGN_WAREHOUSE_MANAGE` (OPERATIONS_MANAGER only) | `{ warehouse_id, expected_version, reason }`. `expected_version` is the `assignment_version` from GET; a stale value returns `VERSION_CONFLICT` 409. The warehouse must be eligible (`WAREHOUSE_NOT_ELIGIBLE` 409) and the campaign must have an area (`CAMPAIGN_AREA_MISSING` 409). | `POST /campaigns/{id}/warehouses/reevaluate` (Idem) | `CAMPAIGN_WAREHOUSE_MANAGE` | `{ clear_manual? }`. Re-ranks the AUTO primary. A MANUAL primary is kept unless `clear_manual` is `true`. Returns the same view. |

Rules:

- **Ranking:** (a) stock for the campaign's open needs (`relief_need` in `OPEN` or `PARTIALLY_FULFILLED` through `fulfillment_cycle.campaign_id`, with `stock_balance.on_hand - reserved > 0` for that item), (b) fewer READY supply requests waiting at the warehouse, (c) shorter distance, (d) smaller warehouse id as the stable tie-break.
- **Sticky:** re-ranking happens only when there is no primary, the primary is ineligible, a warehouse's status, location or radius changed, the campaign area changed, or a manager asked. A warehouse change re-evaluates the campaigns whose cached circle is within reach of the old or new circle, plus campaigns currently assigned to it. A MANUAL primary is never replaced automatically. If it becomes ineligible, the row is kept and flagged.
- **Flags** (derived from state, never stored): `NO_SERVING_WAREHOUSE`, `MANUAL_PRIMARY_INELIGIBLE`, `CAMPAIGN_AREA_MISSING`. A campaign with no eligible warehouse has no `campaign_warehouse` row.
- **Concurrency:** each write evaluation (PUT, POST reevaluate, the sweep, the warehouse trigger) runs in one transaction holding `pg_advisory_xact_lock(hashtext('campaign-warehouse:' || campaign_id))`, and the partial unique index guarantees one PRIMARY. GET takes neither the lock nor a transaction.
- **Triggers** run after the warehouse command commits. A trigger failure is logged with a stable code and never fails the warehouse command.
- **Scheduled sweep:** `CampaignWarehouseService.reevaluateCampaign(campaignId)` is the entry point for the later gap job. It refreshes the snapshot from Response, stores it, and assigns a primary when none exists, so a new campaign gets its primary from the sweep, not from a GET. It throws `RESPONSE_UNAVAILABLE` during an outage. No scheduler is wired in this step.
- **Immediate assignment (2026-11-26).** A new or moved campaign no longer waits for the 15-minute sweep. (1) After a non-replayed activate, resume, `POST /campaigns/{id}/area` or a PATCH that changes `center`/`radius_m`, Response calls `POST /internal/campaigns/{id}/warehouses/sync` (Response service token only; `200 { campaign_id, synced: true }`), which runs `reevaluateCampaign(id, 'CAMPAIGN_CHANGED')`. The call is best effort: the campaign command never waits for it or fails because of it. (2) `GET /need-proposals` assigns a PRIMARY for up to 5 campaigns on the page that have none (`reevaluateCampaign(id, 'PROPOSAL_READ')`); a failure is logged and the proposal is listed without a warehouse. The sweep stays as the last fallback. An SOS has no warehouse of its own: its proposal always uses the current PRIMARY of its campaign.
- **Dependency:** the Response internal projection `GET /internal/campaigns/{id}` must include `center` and `radius_m`. Without them, these endpoints fail closed with `RESPONSE_UNAVAILABLE`.

## 13. SOS need estimates, confirmation and norms (Step 4)

Demand lines stay in `relief_need`; no separate line table exists. Each line has `source`:

- `DECLARED`: entered through `POST /needs` (the existing path).
- `ESTIMATED`: generated by `POST /needs/estimate` from the norm table. Visible in every read, but **never committable**: `POST /needs/{id}/commitments` rejects it with `NEED_ESTIMATE_NOT_CONFIRMED`, and `increase` / `reduce` reject it the same way. `cancel` is allowed.
- `CONFIRMED`: an estimate confirmed by an operations manager. It keeps `estimate` as history.

Only `DECLARED` and `CONFIRMED` count as demand. The fulfillment report, drive suggestions, operations-dashboard need counts and the cycle `has_open_needs` settlement guard exclude `ESTIMATED` lines.

**Estimate rule** (pure function `need-estimate.ts`, no AI, BigInt units only). Let `adults = people - children - elderly`, with `1 ≤ people ≤ 10000` and `children + elderly ≤ people` (otherwise `VALIDATION_FAILED`):

```
BY_GROUP      raw = adults*qty_adult + children*qty_child + elderly*qty_elderly
PER_N_PEOPLE  raw = ceil(people / people_per_unit)   (in whole units)
PER_REQUEST   raw = fixed_quantity
quantity      = raw rounded UP to the item's unit scale (0..3 decimals)
```

A category whose quantity rounds to zero is omitted and reported in `skipped` with `QUANTITY_ZERO`. A quantity above 10^9 whole units is refused (`VALIDATION_FAILED`). A category with no active norm is reported as `NORM_NOT_FOUND` (the command refuses it when the caller named the category).

**Norm table** (`need_norm`, unique `category`): one norm per category with `quantity_basis` (`BY_GROUP`, `PER_N_PEOPLE`, `PER_REQUEST`), the group quantities or the per-unit / fixed value, `default_item_id`, `in_default_bundle` (default true), `active` and `version`. The DB CHECK repeats the basis shape. Seeds (manager-editable, see [seed-logistics.sql](seed/seed-logistics.sql)): `WATER` (`NUOC_UONG`, BY_GROUP adult 3 / child 1 / elderly 2, default the litre item), `FOOD` (`LUONG_THUC`, BY_GROUP 2 / 1 / 1, default the kg item), `BLANKET` (`CHAN_MEN`, PER_N_PEOPLE 1 per 2 people), `MEDICINE` (`Y_TE`, PER_REQUEST fixed 1). A norm's quantity is in the unit of the item used, so the defaults assume the litre water item and the kg rice item.

**Reason codes** (stable English codes, Vietnamese copy in one place, `need-reasons.ts`): `NORM_BY_GROUP`, `NORM_PER_N_PEOPLE`, `NORM_PER_REQUEST`, `DEFAULT_ITEM_USED`, `ROUNDED_UP_TO_UNIT_SCALE`, `NORM_NOT_FOUND` and `QUANTITY_ZERO` (skipped categories), and `QUANTITY_FAR_ABOVE_ESTIMATE`. The retired days and modifier codes are gone.

**Item aliases** (`item.aliases text[]`, at most 20 entries of 1..60 characters, NFC, trimmed): alternative names such as "mì tôm" for "Mì gói". They are read and written by the catalog (`POST /items` takes an optional `aliases`; `PATCH /items/{id}` with `{ expected_version, name?, aliases? }` changes the name and/or replaces the list; `CATALOG_MANAGE`). Matching is pure (`item-aliases.ts`): `normalizeAlias` removes diacritics, maps đ to d, lowercases and collapses spaces, and `matchAliases` returns item ids whose alias occurs as a whole phrase. It is the fallback for AI extraction only; aliases never set a quantity, a stock line or a need.

**`QUANTITY_FAR_ABOVE_ESTIMATE`** is computed on read, never stored. It applies to a live `DECLARED` line whose requested quantity is strictly greater than 3 times the estimated quantity of the latest estimate for the same item in the same cycle, including cancelled or confirmed estimates. A declared line with no earlier estimate is not flagged.

**Read model:** every need row includes `source`, `estimate` (the `estimate_basis` snapshot for ESTIMATED and CONFIRMED lines, otherwise `null`), `estimate_reference_quantity` (DECLARED lines only) and `reason_codes` (the computed flags). The snapshot holds `batch_id`, `category`, `item_type_code`, `item_id`, `norm_id`, `norm_version`, `basis`, `inputs` (`people`, `children`, `elderly`, `adults`, the norm quantities, `raw_quantity`), `estimated_quantity`, `reason_codes` and `estimated_at`.

**Request contract:** the SOS intake contract is unchanged. The coordinator does not type people, days or infant counts; the estimate reads them from the SOS. The web panel shows the estimate read-only and offers "Tạo đề xuất" to operations managers only.

## 14. Supply gaps and manager suggestions (Step 5)

Proposal: [supply-gap proposal §3.4–§3.5](../c48-supply-gap-and-goods-flow-proposal.md). The system only **suggests**. A RED gap becomes a donation drive only when an OPERATIONS_MANAGER accepts it. Nothing here creates a drive by itself. Table: `supply_gap` (migration `AddSupplyGaps1795564800000`; the baseline `schema/logistics.sql` is a frozen historical baseline and is not edited).

**Calculation** (pure function `supply-gap.calculator.ts`, integer units at the item scale, no floats). For each warehouse W and item I:

```
demand     = SUM over relief_need in campaigns whose PRIMARY warehouse is W, source IN (DECLARED, CONFIRMED),
             status IN (OPEN, PARTIALLY_FULFILLED), of max(0, requested - committed)
             committed = SUM(commitment.quantity - commitment.released_quantity) for the need
available  = max(0, on_hand - reserved) at W
pledged    = SUM over drive_item at W of max(0, target - received)
supply     = available + pledged
gap        = demand - supply
```

- `received` is the posted receipt ledger for that drive and item at its intake warehouse (`RECEIPT` and `RECEIPT_HELD_RELEASE` movements). Received stock is already in `on_hand`, so only the unreceived remainder is pledged.
- Drives count as pledges when they are `OPEN`, or when a gap accepted them and they are still `DRAFT` or `PAUSED`. This stops the same gap being suggested again while the accepted draft waits to open.
- `ESTIMATED` lines never count as demand. They are returned as `forecast_demand` on the gap row (computed on read) and never stored.
- Campaigns in `ACTIVE` or `PAUSED` snapshots count. `DRAFT` and `CLOSED` campaigns are ignored.
- Severity: `gap > 0` gives `RED`. Otherwise `supply > 0` and `demand / supply >= 0.8` gives `YELLOW`, a warning with no draft. Demand exactly equal to supply is YELLOW.
- One gap per (warehouse, item). When several campaigns contend, the row lists all of them in `campaign_ids`, largest share first. The draft targets the largest share.
- `backup_warehouse_ids`: BACKUP warehouses of the contending campaigns (other than W) whose `on_hand - reserved` is at least the gap. Nothing is transferred automatically.
- Items are compared only at their own unit scale. Each item has a single unit, so units are never summed.
- Stock is not reassigned and commitments at other warehouses still reduce W's demand. Their reserved stock is excluded from W's supply, so it is not double-counted there.

**Recompute** (`SupplyGapsService.recompute`): first calls `CampaignWarehouseService.reevaluateCampaign` for at most 50 campaigns that have no PRIMARY (ACTIVE snapshots, plus campaigns with live needs). Then each warehouse is recomputed in its own transaction under `pg_advisory_xact_lock(hashtext('supply-gap:' || warehouse_id))`. The `OPEN` row is refreshed by `INSERT … ON CONFLICT (warehouse_id,item_id) WHERE status='OPEN' DO UPDATE`, and its version increases only when the content changes. A gap that disappears moves to `EXPIRED`. Failures are logged with a stable code and never thrown to callers. Audit rows: `SUPPLY_GAP_OPENED` and `SUPPLY_GAP_EXPIRED` (actor null, reason `SUPPLY_GAP_RECOMPUTED`).

**Draft** (RED only): `{ title: 'Quyên góp bổ sung {item}', description, intake_warehouse_id, campaign_id (largest share), opens_at, closes_at, items: [{ item_id, target_quantity: ceil(gap × 1.10) at the item scale, acceptance_note }] }`. The window is `now` to `now + 7 days`, kept while it is still open and refreshed after it closes.

**Cooldown after dismissal:** a dismissed RED gap reopens only when the current RED gap is at least 1.25 × the dismissed gap. A dismissed YELLOW warning reopens only when it becomes RED. The cooldown ends at `dismissed_until`, after which the gap may reopen normally.

**Scheduler:** `SupplyGapScheduler` runs the recompute every 15 minutes through the shared `JobRunner` (advisory lock per job name). Environment `C48_SUPPLY_GAP_JOB_ENABLED`: unset or `true` enables it, `false` disables it, and any other value fails startup. Recompute is not hooked into need or stock commands in this step. The scheduler covers the 15-minute cadence.

**Permissions:** `SUPPLY_GAP_VIEW` (OPERATIONS_MANAGER only, read-only; user decision 2026-11-22) for the GET routes. `SUPPLY_GAP_MANAGE` (OPERATIONS_MANAGER, SYSTEM scope) for accept and dismiss. Both need a SYSTEM grant, because a warehouse gap is not scoped to one campaign.

| Method & path | Auth | Behaviour |
|---|---|---|
| `GET /supply-gaps?status=&warehouse_id=&cursor=&limit=` | `SUPPLY_GAP_VIEW` | Keyset page (default 50, maximum 100), newest first. Each row carries demand, supply, pledged, gap_qty, forecast_demand, campaign_ids, backup_warehouse_ids, reason_codes, `reasons` (`{code, message}` with Vietnamese copy), draft, drive_id, dismissal data, version. Quantities are decimal strings at the item scale. `no-store`. |
| `GET /supply-gaps/{id}` | `SUPPLY_GAP_VIEW` | One row, same shape. |
| `POST /supply-gaps/{id}/accept` (Idem) | `SUPPLY_GAP_MANAGE` | `{ expected_version, overrides?: { title?, description?, items?, opens_at?, closes_at? } }`. Only a RED `OPEN` gap. ## 15. Need extraction sweep and manager proposals (Step 7)

No quantity comes from AI: Gemini (or the alias matcher) chooses catalog items, and the norm estimator (§13) computes every quantity. Code: `backend/apps/logistics/src/need-extraction/`.

**Input.** The sweep reads `GET /internal/requests/supply-candidates` on Response (§11 there). It uses `relief_items_text` and the SOS people counts. A request with `people_affected` null is recorded as `SKIPPED` (`NEED_PEOPLE_MISSING`).

**Choosing items (source order).**
1. `GEMINI`: the sanitized text and the ACTIVE catalog (at most 300 items: id, name, first five aliases) go to Gemini in JSON mode. The schema has `item_ids` (array whose items are an enum of catalog ids, at most 20) and `unmatched_terms` (at most 10, each at most 60 characters). There is no quantity field. The prompt (Vietnamese) states that the citizen text is untrusted data. Server validation drops ids outside the catalog and duplicates, and caps the lists.
2. `ALIAS`: when Gemini is not configured, the daily quota is reached, the call times out or fails, the output is invalid, or it yields no line. `matchAliases` (whole phrase, after normalization) on the sanitized text, ordered by first mention.
3. `DEFAULT_BUNDLE`: empty text, or nothing matched. Every active norm with `in_default_bundle = true` whose default item is an ACTIVE catalog item.

**Mapping.** One line per category (the norm whose `item_type_code` matches the item's type). The first mentioned item of a category is that line. Other mentioned items are kept only in `extraction.mentioned_items`. Nothing is split or summed.

**Sanitizer.** Before Gemini or logging, the text loses e-mail addresses, URLs, phone numbers (`0…` or `+84…`, with optional separators) and digit runs of six or more digits. It is NFC-normalized, whitespace is collapsed and it is cut to 500 characters.

**Persistence.** The sweep calls `persistEstimateBatch` (shared with `POST /needs/estimate`), so the cycle lock, norm and item checks, `NEED_ALREADY_DECLARED` and the one-live-need index apply. Its actor is SYSTEM: no grant check, and `audit_log` rows `NEED_ESTIMATED` with a null actor. Each line stores `estimate_basis.extraction = { source, reason_codes, unmatched_terms, mentioned_items: [{ item_id, category }], model? }`. Reason codes and Vietnamese copy: `EXTRACTED_FROM_TEXT`, `ALIAS_MATCHED`, `DEFAULT_BUNDLE_USED`, `UNMATCHED_TERMS` (`need-reasons.ts`).

**Sweep and idempotency.** `NeedExtractionScheduler` runs every 5 minutes through `JobRunner` (advisory lock on `logistics.need-extraction-sweep`; one run at a time across replicas). `C48_NEED_EXTRACTION_JOB_ENABLED`: unset or `true` enables it, `false` disables it, any other value fails startup. A run pages through at most 10 pages of 50 candidates and attempts at most 20 requests that have no `need_extraction_log` row. Gemini is called outside the database transaction; the write is one transaction per request, so one failure never stops the run.

`need_extraction_log (request_id, work_cycle)` is the primary key and records the decision:
- `CREATED`: lines written (source recorded).
- `NO_LINES`: the rule produced no line (for example, no active norm). Not retried.
- `SKIPPED`: `NEED_PEOPLE_MISSING`, or `NEED_LINE_EXISTS` (the cycle already has any need line; manual lines are never overwritten).
- `FAILED`: a stable `AppError` code from the core (for example `NEED_ALREADY_DECLARED`, `CYCLE_FROZEN`). Not retried automatically; delete the row to reprocess.
A database error (not an `AppError`) records nothing, so the request is retried on a later run.

**Quota.** `need_extraction_daily_usage (usage_date, calls)` counts Gemini calls per `America/Los_Angeles` date. `GEMINI_DAILY_CALL_LIMIT` keeps its existing meaning (unset or 0: no cap). Response keeps its own counter in its own database, so the two services do not share one count.

**Manager read model.**

| Route | Permission | Behaviour |
|---|---|---|
| `GET /need-proposals?cursor=&limit=` | `NEED_ESTIMATE_CONFIRM` (OPERATIONS_MANAGER; SYSTEM scope sees all campaigns, CAMPAIGN scope only its campaigns; other callers `FORBIDDEN` 403) | Read-only, `no-store`, keyset on cycle id (`CURSOR_INVALID`), default 50, maximum 100. One item per (request, work cycle) that has OPEN ESTIMATED lines: `sos` (`people`, `children`, `elderly`, `adults` from `estimate_basis.inputs`), `warehouse` (campaign PRIMARY, or `null`), `lines` (`need_id`, `version`, `category`, `item {id,name,unit}`, `quantity`, `available` = on_hand − reserved at the PRIMARY with a floor of 0, `shortfall` = quantity > available, `reason_codes`, `reasons` `{code,message}` in Vietnamese), `extraction` (`source`, `model`, `unmatched_terms`, `mentioned_items` with names, `reasons`) or `null`, and `generated_at`. `available` and `shortfall` are `null` when the campaign has no PRIMARY warehouse. |

**SOS outside every campaign (decided 2026-11-19).** The chain stays SOS → campaign → warehouse. An SOS with no campaign still gets ESTIMATED lines (the sweep creates its cycle with `campaign_id` NULL), but those lines belong to no warehouse and never enter demand or any supply gap. `GET /need-proposals` lists only campaign cycles (`campaign_id IS NOT NULL`). `?campaign_scope=NONE` lists only cycles with `campaign_id` NULL ("Chưa thuộc chiến dịch nào"); it needs SYSTEM scope (`FORBIDDEN` 403 for a campaign-scoped manager). A SYSTEM-scope response also carries `unassigned_total`: the number of such cycles that still hold an OPEN ESTIMATED line. It is awareness only and is never added to a gap number. The manager may still confirm or reject such a line; warehouse stock cannot be compared and no donation proposal is computed until the SOS is attached. The coordinator fixes it in Response by attaching the SOS to a campaign (`POST /requests/{id}/attach-campaign`, `MANUAL`), widening a campaign area, or creating a campaign from the SOS map. Logistics then lets the cycle adopt the campaign: `adoptCycleCampaigns` sets `fulfillment_cycle.campaign_id` only when the cycle is OPEN, has no live `cycle_intent`, has no non-ESTIMATED need, and no commitment or pickup line. It runs when the cycle is next locked (estimate, intent) and on every need-extraction sweep for already processed candidates that now carry a campaign (runs every 5 minutes), so the lag is bounded by the sweep interval. Any other cycle keeps its copied attribution, which stays historical.

**Approve and reject.** No new write route. Approve with `POST /needs/{id}/confirm` (`expected_version`, optional `quantity`, `reason`, `item_id`; OPEN cycles only). Reject with `POST /needs/{id}/cancel` (`expected_version`, `reason`; `NEED_MANAGE` in cycle scope, allowed for ESTIMATED lines). Both read the cycle's `campaign_id`, which the sweep stores from the same SOS attribution, so the existing scope rules apply to sweep-created lines.

**Known limits.**
- The sweep only creates ESTIMATED lines. Lines for requests whose cycle is FROZEN or SEALED fail with that code and are recorded `FAILED`.
- A SOS without a campaign produces lines only SYSTEM managers can see (the same as the manual estimate).
- Gemini sees the first 300 ACTIVE items by name. Default-bundle items outside that window are not used.
- Requests with a supplement waiting for review are not scanned until it is reviewed.
- The new SQL has not been run against PostgreSQL in this change (no Docker run was allowed). Gemini has not been called live; tests use a fake client and a mocked `fetch`.
