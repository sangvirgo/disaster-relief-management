# 03 — Response service: API contract

Schema: [schema/response.sql](schema/response.sql). Conventions: [00](00-setup.md). Permissions: [05](05-permissions.md). State rules: plan §8.1–8.2, §22, §23.2, §26. "Idem" = `Idempotency-Key` required. "Ver" = `expected_version` in body required. Authenticated = session + Identity introspection. Every command writes (same local transaction): state change, `request_event`/`mission_event`/`audit_log`, and notices.

## 1. Request intake and tracking

### `POST /requests` — create SOS (SELF, guest or signed-in) · Idem · public, throttled
Headers: `Idempotency-Key`; guest also `X-Tracking-Secret: <secret>`; signed-in optional bearer/cookie. SELF intake validates the access-token signature locally. Capability-authenticated tracking, supplement, and evidence operations do not call Identity; account-owner access, claim, and recovery introspect live Identity sessions.
```json
{ "incident_category_code": "FLOOD", "description": "…≤2000", "people_affected": 3,
  "children_count": 1, "elderly_count": 1,
  "reporter_name": "optional", "reporter_contact_phone": "0912345678",
  "reporter_declared_danger": false, "needs_rescue": true, "needs_relief_supplies": false,
  "location": { "type": "Point", "coordinates": [106.70, 10.77], "source": "GPS", "accuracy_m": 12.0, "captured_at": "2026-10-07T08:30:00Z" } }
```
`201 { id, tracking_code, status: "SUBMITTED", received_at, review_lane }` (replay returns the same creation representation + `Idempotent-Replay`, even after later status transitions). `location.source ∈ GPS|MANUAL_PIN`; GPS requires both `accuracy_m` and `captured_at`; manual pin must omit `accuracy_m`. Description/media are optional; people_affected, children_count, elderly_count and reporter_contact_phone may be omitted/null when unknown. Supplied counts are integers; children + elderly may not exceed `people_affected` when it is known. `needs_rescue` defaults to `true`, `needs_relief_supplies` defaults to `false`, and at least one must be true. The existing dangerous-life flag is a reporter declaration, separate from computed risk. Supplied phone normalizes to optional+ and8–15 digits. No citizen item/quantity input. Server: derives `region_code` only when exactly one boundary covers the point (no match or ambiguous overlaps ⇒ null, request still stored in the unassigned queue), assigns demo intake organization, stores `tracking_secret_hash` (purpose-bound), creates request + subject + REPORTER-visible event "received" atomically; soft throttle breach (per-IP `source_ip_hash` count via `request_source_ip_idx`, per-phone `request_phone_idx` count, or the global `SOS_GLOBAL_PER_MIN` ceiling) ⇒ stored with `review_lane=RATE_LIMITED_REVIEW`; only the per-IP **hard** Nginx ceiling returns `429 SOS_RATE_CEILING`. `source_ip_hash` is purpose-bound and never stores the raw address. A cookie-authenticated call needs the CSRF token (00 §3.3). `tracking_code` is generated server-side from a CSPRNG (collision ⇒ `ON CONFLICT` retry, never inside an aborted transaction).
Errors: `VALIDATION_FAILED` (`COORDINATES_OUT_OF_RANGE`, `PEOPLE_AFFECTED_OUT_OF_RANGE`, `VULNERABLE_COUNT_EXCEEDS_TOTAL`, `AT_LEAST_ONE_NEED_REQUIRED`, `PHONE_INVALID`, `CATEGORY_UNKNOWN`, `ACCURACY_REQUIRED`), `TRACKING_SECRET_INVALID` 400, `TRACKING_SECRET_IN_USE` 409 (generic, reveals nothing), `IDEMPOTENCY_KEY_REUSED` 409, `SOS_RATE_CEILING` 429 (Vietnamese hard-limit message with 113/114/115 guidance).

### Rules risk score and Gemini priority advisory

Response calculates an explainable `priority_advisory` from SOS facts, including flood/trapped indicators, children, older people, large affected groups, injuries and requested rescue. A reporter-declared life-danger flag remains a separate coordinator filter/alert and does not add to the backend rule score. The result is a suggestion with bands `CRITICAL` (70+), `HIGH` (45–69), `ELEVATED` (20–44) and `STANDARD` (0–19) when the report has direct risk evidence. Without direct narrative evidence of immediate danger or injury, `outcome` is `INSUFFICIENT_DATA` and `score`/`level` are null; the rules do not imply a low-risk `STANDARD` result from missing evidence. Until validated medical scoring rules exist, descriptions that mention breathing difficulty, unconsciousness, fainting or emergency care also return null with an urgent human-review reason. This lightweight advisory remains available when Gemini is disabled, overloaded or at quota. It never changes official priority or queue order.

Relevant accepted SOS reports and later material fact changes enqueue an asynchronous AI advisory job. The Response worker always polls this queue without a separate enable flag. When `GEMINI_API_KEY` is configured, Response sends only structured SOS facts by default (category, declared counts, danger declaration and requested assistance flags) to `GEMINI_MODEL` (default `gemini-3.5-flash-lite`). Free-text descriptions, contact details, exact coordinates and evidence files are excluded. `GEMINI_INCLUDE_SYNTHETIC_DEMO_NARRATIVE=true` explicitly adds a masked description for synthetic demonstrations only. Masking covers common identifiers but can miss personal information; keep this setting false for real SOS data. A provider, storage and retention decision is still required before real sensitive data is sent externally. Gemini returns a Vietnamese summary, indicators, extracted facts, a suggested risk score from 0–100, short reasons and self-reported confidence. The queue and detail expose this separately as `ai_priority_advisory`, with source `GEMINI` or `DEMO_FIXTURE`; the existing `ai_advisory` also carries extraction and review data. HTTP 408/429/5xx and network failures are retried with bounded exponential backoff. `GEMINI_MAX_RETRIES` sets retries after the initial provider call (default `3`, so at most four calls per job); `0` disables automatic retries. If the daily call cap is reached, queued work is deferred until the next `America/Los_Angeles` date. Every provider call, including retries, counts toward the 500-call daily cap. Permanent provider errors and invalid model output are recorded as failed. Expired processing leases are requeued while retry budget remains; a fresh claim token prevents an older worker from committing after recovery. Missing keys do not block SOS intake or the backend rule advisory.

Seeder-generated results use model names prefixed with `demo-fixture:` and are surfaced as `DEMO_FIXTURE`. They exist only to demonstrate the UI and are not live model assessments. A real Gemini result and a demo fixture both remain untrusted suggestions requiring coordinator review.

The database enforces a hard application cap of 500 Gemini calls per `America/Los_Angeles` calendar day for the shared Response deployment. This is a local cap; Google’s actual provider quota is separate and may vary by project/tier. Queue order stays fixed by `received_at ASC, id ASC`; neither advisory sorts the queue, changes official P1–P4 priority or assigns a team. Advisory results become `STALE` after material SOS facts change, and their scores/reasons are withheld until a fresh assessment is available. `POST /requests/{id}/ai-advisories/{advisoryId}/review` with `{ expected_version, decision: ACCEPTED|ADJUSTED|REJECTED, note? }` records the coordinator’s human review; `ADJUSTED` requires a note. Review checks the current request version and advisory input hash; stale decisions return `409 VERSION_CONFLICT`. `POST /requests/{id}/ai-advisories/{advisoryId}/retry` with `{ expected_version }`, `Idempotency-Key`, and `REQUEST_VERIFY` scope returns `202 { request_id, advisory_id, status: QUEUED }` for the latest fresh `FAILED` advisory when Gemini is configured. It resets that advisory’s retry counter and appends an `AI_ADVISORY_RETRY` staff event; retries are idempotent and do not change SOS facts, official priority or team assignment. Both endpoints preserve the coordinator’s human authority.

### `POST /requests/proxy` — report for a household · Idem · live session required (**always introspected**)
Body as above plus required `relationship`, `information_source`, `last_known_situation_at` (UTC ISO-8601 timestamp ending in `Z`), and `contactability`; optional `beneficiary_contact_phone` and `alternate_contact { name, phone? }`. Affected-person account/phone is not required. `location` is the **household's** pin and determines the region (the reporter's GPS is not accepted). The reporter's `reporter_contact_phone` remains optional and distinct from the beneficiary phone. → `201` same shape. Beyond `PROXY_OPEN_CAP` simultaneously unverified (`SUBMITTED`/`VERIFYING`) reports or `PROXY_DAILY_SOFT_LIMIT` reports in the rolling 24 hours, the report is still stored with `review_lane=PROXY_QUOTA_REVIEW`. These are soft check-then-insert limits, so concurrent requests may overshoot; no request is dropped. Defaults: open cap 3 and daily soft limit 10. A proxy quota lane takes precedence over the generic `RATE_LIMITED_REVIEW` lane if both apply. Identity outage ⇒ `503 IDENTITY_UNAVAILABLE`; expired/revoked session ⇒ `401`; the request is never retried as SELF. Cookie-authenticated writes require an allowed Origin and CSRF token. Nginx applies the SOS hard per-IP ceiling to this path too.

When the account or reporter phone has at least three distinct PROXY household locations (rounded to ~100 m cells) in the previous 24 hours, or has any previously rejected report, Response appends a `PROXY_ACTIVITY_FLAG` staff-only event with counts, up to ten recent PROXY request IDs, and up to ten IDs of previously rejected requests (SELF or PROXY). This heuristic is informational; it never blocks the reporter or changes status/priority. The 10/day threshold and 3-location/24-hour flag trigger are configurable/provisional demo policy and need field calibration before operational use. The coordinator queue/detail surface for these staff-only facts is delivered with T7.

### Lost tracking secret (plan R-17)
`POST /requests/{id}/tracking-secret/revoke` · Idem · Ver · REQUEST_VERIFY + scope clears the old secret only; revocation does not enable claim without proof. Assisted recovery is explicit:

| Route | Authorization / DTO / result |
|---|---|
| POST /requests/{id}/recovery · Idem · Ver | REQUEST_VERIFY + scope; `{expected_version,reason,contact_attempt_id,source_note}` requires independently verified successful reporter contact, not phone/name knowledge alone. Returns201 `{issuance_id,recovery_code,expires_at}`. |
| POST /requests/recover · Idem | Live session + X-Recovery-Code; `{tracking_code}` binds an unowned request once, clears code/old secret, returns200 `{id,tracking_code}`. Wrong/expired/consumed code gives generic404. |

Code is random, purpose/object-bound, hashed and expires 30 minutes; issuance replaces old code. Plaintext is returned once; same issuance-key replay returns original 201 with safe issuance metadata only. Other commands replay original response/status. Lost initial issuance response requires a new verified issuance. Recovery uses `capability_recovery` from the T0-S schema. Native claim uses Bearer plus X-Tracking-Secret; Web uses cookies plus that header; never two Authorization values.

## 6. Evidence upload (requests and missions)

`POST /requests/{id}/evidence` is implemented in T5; mission evidence follows with T9. Multipart accepts one file per call and requires `Content-Length` (`411`). It streams to a temporary file with a 55 MiB body cap and media-specific limits (JPEG/PNG ≤ 10 MiB; MP4 ≤ 50 MiB; reject SVG/HTML/others), ignores the client filename/MIME, detects type from the first 4 KiB, and calculates SHA-256. Before the object-store write, a short transaction locks the request, checks count ≤ 5 READY/PENDING and aggregate ≤ 100 MiB (including `declared_bytes` of PENDING), checks the guest's 200 MiB/hour byte budget, and inserts `PENDING` metadata with a purpose-bound `upload_source_ip_hash` (never raw IP). The object is written to a generated immutable key outside the transaction; a second short write sets READY with size, MIME, and checksum. Storage failure leaves the SOS unchanged and evidence `FAILED`; retry uses a new idempotency key. The scheduler (advisory-locked, 00 §3.2) reconciles `PENDING` older than 15 minutes and retries old `FAILED` object cleanup until deletion succeeds, recorded by `cleanup_completed_at`. `GET /evidence/{id}/download` authorizes against the owning request and returns `{ url, expires_in: 60 }`. S3 signatures use `S3_PUBLIC_ENDPOINT`, routed through Nginx to the private bucket; the object proxy strips API credentials and sets `Cache-Control: no-store`. Errors: `EVIDENCE_LIMIT_REACHED`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA`, `STORAGE_UNAVAILABLE` 503. `shortcut:` MP4 checks its ISO-BMFF container signature but does not inspect H.264/AAC tracks; add a bounded container-side `ffprobe` check before accepting untrusted production video.

## 7. State and invariants to enforce in code

Request transitions exactly as plan §8.1 diagram; mission as §8.2; DISPATCHED/IN_PROGRESS recomputed from missions (accepted/en-route/on-scene ⇒ IN_PROGRESS; else any OFFERED ⇒ DISPATCHED; else TRIAGED unless human terminal outcome); lock order and modes per 00 §3.1 (campaign `FOR SHARE`/`FOR UPDATE` → request `FOR UPDATE` → team → team_member → mission). Material progress recompute increments request version; no-op work does not. Every mutation respects the parent lock/barrier. Reopen increments `work_cycle`, tags new missions, and **clears** `resolved_at` and `resolution_seal_id` (DB CHECKs require both for RESOLVED/CLOSED and forbid one without the other). Entering VERIFYING sets `verifying_since`. While RESOLVING reject offers, progress, supplements, cancel, competing resolve. Priority never affects queue order or dispatch. AI remains optional and human-reviewed; it cannot set official priority or dispatch. Push notifications and CSV export remain outside this implementation.
