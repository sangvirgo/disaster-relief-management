# 03 — Response service: API contract

Schema: [schema/response.sql](schema/response.sql). Conventions: [00](00-setup.md). Permissions: [05](05-permissions.md). State rules: plan §8.1–8.2, §22, §23.2, §26. "Idem" = `Idempotency-Key` required. "Ver" = `expected_version` in body required. Authenticated = session + Identity introspection. Every command writes (same local transaction): state change, `request_event`/`mission_event`/`audit_log`, and notices.

## 1. Request intake and tracking

### `POST /requests` — create SOS (SELF, guest or signed-in) · Idem · public, throttled
Headers: `Idempotency-Key`; guest also `Authorization: C48-Tracking <secret>`; signed-in optional bearer/cookie (ownership link only — validated by **signature only**, no introspection).
```json
{ "incident_category_code": "FLOOD", "description": "…≤2000", "people_affected": 3,
  "reporter_name": "optional", "reporter_contact_phone": "0912345678",
  "reporter_declared_danger": false,
  "location": { "type": "Point", "coordinates": [106.70, 10.77], "source": "GPS", "accuracy_m": 12.0, "captured_at": "2026-10-07T08:30:00Z" } }
```
`201 { id, tracking_code, status: "SUBMITTED", received_at, review_lane }` (replay returns the same body + `Idempotent-Replay`). `location.source ∈ GPS|MANUAL_PIN`; GPS requires `accuracy_m`; manual pin must omit it. Description/media are optional; people_affected and reporter_contact_phone may be omitted/null when unknown. Supplied count is integer1..10000; supplied phone normalizes to optional+ and8–15 digits. No citizen item/quantity input. Physical nullability changes are pending T0-S (01 §7). Server: derives `region_code` by `ST_Covers(region_boundary)` (no match ⇒ null, request still stored), assigns demo intake organization, stores `tracking_secret_hash` (purpose-bound), creates request + subject + REPORTER-visible event "received" atomically; soft throttle breach (per-IP Nginx zone, per-phone `request_phone_idx` count, or the global `SOS_GLOBAL_PER_MIN` ceiling) ⇒ stored with `review_lane=RATE_LIMITED_REVIEW`; only the per-IP **hard** ceiling returns `429 SOS_RATE_CEILING`. `source_ip_hash` is stored. A cookie-authenticated call needs the CSRF token (00 §3.3). `tracking_code` is generated server-side from a CSPRNG (collision ⇒ `ON CONFLICT` retry, never inside an aborted transaction).
Errors: `VALIDATION_FAILED` (`COORDINATES_OUT_OF_RANGE`, `PEOPLE_AFFECTED_OUT_OF_RANGE`, `PHONE_INVALID`, `CATEGORY_UNKNOWN`, `ACCURACY_REQUIRED`), `TRACKING_SECRET_INVALID` 400, `TRACKING_SECRET_IN_USE` 409 (generic, reveals nothing), `IDEMPOTENCY_KEY_REUSED` 409, `RATE_LIMITED` 429 (with 113/114/115 text).

### `POST /requests/proxy` — report for a household · Idem · session required (**always introspected**)
Body as above plus `relationship` (required), `beneficiary_contact_phone?`, `alternate_contact { name, phone? }?`, `information_source`, `last_known_situation_at`, `contactability`. `location` is the **household's** pin (never the reporter's GPS). → `201` same shape. Beyond `PROXY_OPEN_CAP` open reports for the account ⇒ stored with `review_lane=PROXY_QUOTA_REVIEW` (never dropped). Identity outage ⇒ `503 IDENTITY_UNAVAILABLE` (client must not retry as SELF). Errors add `RELATIONSHIP_REQUIRED`.

### Lost tracking secret (plan R-17)
`POST /requests/{id}/tracking-secret/revoke` · Idem · Ver · REQUEST_VERIFY + scope clears the old secret only; revocation does not enable claim without proof. Assisted recovery is explicit:

| Route | Authorization / DTO / result |
|---|---|
| POST /requests/{id}/recovery · Idem · Ver | REQUEST_VERIFY + scope; `{expected_version,reason,contact_attempt_id,source_note}` requires independently verified successful reporter contact, not phone/name knowledge alone. Returns201 `{issuance_id,recovery_code,expires_at}`. |
| POST /requests/recover · Idem | Live session + X-Recovery-Code; `{tracking_code}` binds an unowned request once, clears code/old secret, returns200 `{id,tracking_code}`. Wrong/expired/consumed code gives generic404. |

Code is random, purpose/object-bound, hashed and expires30min; issuance replaces old code. Plaintext is returned once; same issuance-key replay returns original201 with safe issuance metadata only. Other commands replay original response/status. Lost initial issuance response requires a new verified issuance. Paired hash/expiry columns are a pending T0-S delta. Native claim uses Bearer plus X-Tracking-Secret; Web uses cookies plus that header; never two Authorization values.

## 6. Evidence upload (requests and missions)

`POST …/evidence` multipart, one file per call, Idem. Requires `Content-Length` (`411`), a streaming byte counter and the guest limits of 00 §3.3. Steps: authorize owner object → in a short transaction lock the owner row, check count ≤ 5 READY/PENDING and aggregate ≤ 100 MiB (including `declared_bytes` of PENDING), insert `PENDING` row with `declared_bytes` (from `Content-Length`; reject over limit) → stream to a generated immutable key (`req/{id}/{uuid}` or `mission/{id}/{uuid}`) outside any transaction with a byte cap → detect real type (JPEG/PNG ≤ 10 MiB; MP4 H.264/AAC ≤ 50 MiB; reject SVG/HTML/others) → second short transaction sets READY with size, mime, checksum. Failure leaves the SOS intact and the row `FAILED` (retryable by a new upload). The scheduler (advisory-locked, 00 §3.2) reconciles `PENDING` older than 15 min with `UPDATE … WHERE state='PENDING' RETURNING` and deletes the object only if it won the race. `GET /evidence/{id}/download` → authorizes on the owning object then returns `{ url, expires_in: 60 }`. Errors: `EVIDENCE_LIMIT_REACHED`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA`, `STORAGE_UNAVAILABLE` 503.

## 7. State and invariants to enforce in code

Request transitions exactly as plan §8.1 diagram; mission as §8.2; DISPATCHED/IN_PROGRESS recomputed from missions (accepted/en-route/on-scene ⇒ IN_PROGRESS; else any OFFERED ⇒ DISPATCHED; else TRIAGED unless human terminal outcome); lock order and modes per 00 §3.1 (campaign `FOR SHARE`/`FOR UPDATE` → request `FOR UPDATE` → team → team_member → mission). Material progress recompute increments request version; no-op work does not. Every mutation respects the parent lock/barrier. Reopen increments `work_cycle`, tags new missions, and **clears** `resolved_at` and `resolution_seal_id` (DB CHECKs require both for RESOLVED/CLOSED and forbid one without the other). Entering VERIFYING sets `verifying_since`. While RESOLVING reject offers, progress, supplements, cancel, competing resolve. Priority never affects queue order or dispatch. **Not implemented here:** AI tables/endpoints (plan §12, optional), push notifications, CSV export.

## 9. Focused logic contracts (plan §27; pending schema alignment)

- GET /request-categories is public sanitized paginated catalog; GET /skills requires a session. No new unsolicited operational permissions.
- POST /teams/{id}/ready (Idem/Ver): active APP leader or TEAM_MANAGE_ANY + scope; `{expected_version,confirmation_basis,reported_by?,occurred_at}`. Coordinator requires reported_by. No active mission; clears readiness latch and sets AVAILABLE atomically; stale version fails.
- POST /teams/{id}/verify-affiliation (Idem/Ver, TEAM_MANAGE_ANY+scope) records basis/source and verifier/time; affiliation never grants authority.
- Verify appends immutable approved snapshot event; request.verification_revision points to same-request snapshot. Existing subject fields are approved spatial/list projection; mission.verification_revision is immutable offer-time snapshot. Source refs must exist, be scoped and independently attributable; no IP-only verdict.
- POST /requests/{id}/supplements/{event_id}/review (Idem/Ver, REQUEST_VERIFY+scope), `{expected_version,decision:ACCEPT|REJECT,reason,source_refs?,source_note?}` creates one final review per material event; ACCEPT creates a full approved snapshot and updates subject projection/pointer atomically, REJECT retains prior approved facts. Existing missions retain destination. New triage/offer/resolve requires pending material review cleared.
- POST /internal/requests/{id}/cycles/{work_cycle}/admit: Logistics service + signed live NEED_MANAGE actor; business-tuple idempotency. Under Response request lock, require eligible current cycle/campaign/scope and no pending follow-up; set attribution_locked_at if absent, bump version and return canonical organization/region/campaign/version.
